## 1. Headline

**The Perl side performs no renderer selection at all.** Across the launcher, every `cx*` script, `lib/perl/*.pm`, `lib/cxupgrade`, the 13 bottle templates, `etc/CrossOver.conf`, `bottle_data/{cxbottle.conf,crossover.inf}`, `share/wine/wine.inf`, `cxfixes.xml` and `crossover.tie`, the only renderer-related logic is:

1. unconditional export of `CX_APPLEGPTK_LIBD3DSHARED_PATH` (SH-TT-19, `wine:679-684`);
2. pass-through of the bottle's `[EnvironmentVariables]` (SH-TT-08, `CXBottle.pm:9-39`);
3. a one-shot **migration** of legacy keys at bottle-upgrade time (`upgrade_graphics_settings`, `CXBT:448-467`);
4. `WINEDLLPATH` that never includes `lib/dxmt`, `lib/dxvk` or `lib64/apple_gptk/wine` (SH-TT-30, `wine:656-671`).

Everything else (reading `CX_GRAPHICS_BACKEND`, the per-game "Auto" database, prepending the right DLL directory, setting `CX_ACTIVE_GRAPHICS_BACKEND`) must therefore happen in a binary. The LGPL tree shows the hook (`prepend_dll_path`, dlopen of `cxcompatdb.so`), so the inferred owner is `cxcompatdb.so`. This pass can only mark that as **inferred**; the binary pass (strings/exports/imports of `cxcompatdb.so`, Ghidra on `ntdll.so`) must confirm it.

## 3. What this means for ossover (H2 overlay strategy)

* **Confirmed**: nothing in CX's plumbing needs the prefix to contain renderer DLLs; CX selects by Unix-side DLL search path. The plan's strategy C (`WINEDLLPATH_PREPEND` patch on our engine) reproduces exactly what `prepend_dll_path` offers, and strategy B (`WINEDLLPATH` first component = `<pack>/wine`) is the only plain-env equivalent because the shipped `WINEDLLPATH` already lists `lib/wine/x86_64-windows` first and Wine's loader stops at the first match (inferred from `loader.c:389`/`682`, not re-verified here).
* **Caveat for strategy B on the CX bootstrap engine**: `lib/wine/x86_64-windows` already contains a `winemetal.dll` and wined3d `d3d11.dll`/`dxgi.dll`/`d3d10core.dll`; whatever we prepend must shadow all four (`d3d11`, `dxgi`, `d3d10core`, `winemetal` + Unix `winemetal.so`), matching the exact file set in `lib/dxmt/x86_64-{windows,unix}` (SH-TT-56). **Superseded by ledger L-20 / decision 12** (binary pass + `loader.c:387-408`, `1595-1632`, `1655-1658`): `WINEDLLPATH` cannot shadow `dll_dir` entries at all, and a builtin-marked `winemetal.dll` placed in the prefix only redirects to the engine's own pair; under strategy B only `d3d11`/`dxgi`/`d3d10core` can be replaced (mark-stripped prefix copies) while the engine's `winemetal.{dll,so}` stay in use.
* **Do not** emulate `CX_GRAPHICS_BACKEND`; emulate `CX_ACTIVE_GRAPHICS_BACKEND` on CX-derived engines (readers confirmed, SH-TT-59) — set `wined3d`/`dxvk`/`dxmt`/`d3dmetal` from the `renderer` setting. For `d3dmetal` this flips `d3dkmt` HwSch caps; for `wined3d` it enables `CX_LIBVULKAN`.
* **Open for the binary pass**: (a) exports/imports/strings of `cxcompatdb.so` — expected: imports `prepend_dll_path`, strings `CX_GRAPHICS_BACKEND`, `WINED3DMETAL`, `WINEDXVK`, `dxmt`, `dxvk`, `d3dmetal`, directory names `lib/dxmt`, `lib/dxvk`, `apple_gptk/wine`, and the embedded per-app database (Steam/Witcher app ids?); (b) the exact DXMT value spelling; (c) how "Auto" resolves for `witcher3.exe`.
